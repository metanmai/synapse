# Phase 2 — UI Design Contract

> Visual and interaction contract for the **one** Phase 2 UI surface: "Link to existing project" button + project-picker modal + confirmation step. Generated by gsd-ui-researcher per locked decision D-07 in `02-CONTEXT.md`. Consumed by gsd-planner, gsd-executor, and gsd-ui-checker.

---

## Phase UI Scope

Phase 2 ships **one button + one modal + one endpoint** (per D-07, locked in `02-CONTEXT.md`):

- **Button:** "Link to existing project" — surfaces inside the per-project Settings page (sibling to the existing Members section). Triggers the project-picker.
- **Modal-equivalent:** project-picker UI (auto-match candidates at top, full list below) with a two-step type-to-confirm destructive gate. **Implemented as an inline-expanding card on the Settings page**, NOT a floating dialog overlay — matches the existing destructive-action pattern in `frontend/src/lib/components/account/DangerZone.svelte` (reset / delete account). The project has no floating-modal component today; introducing one is scope creep.
- **Endpoint:** `POST /api/projects/:id/merge-into/:target_id` — frontend calls via SvelteKit form action. Backend shape locked in `02-RESEARCH.md` §"Common Operation 4".

**Out-of-scope reminder (do not design):** identity bootstrap (CLI-only), cross-device auto-detect (daemon-only), brief device-origin string (CLI renderer), separate merge-history page, dashboard-list inline merge action, mobile-specific flow, redesign of any existing surface.

## Surfaces

Phase 2 introduces **exactly one new surface**, hosted inside an **existing** route (`/projects/[name]/settings`). Section ordering: existing "Members" → NEW "Linked Projects".

### Surface 1: "Linked Projects" section on Project Settings page

**Location:** `frontend/src/routes/(app)/projects/[name]/settings/+page.svelte` — add a new `<section>` below the existing Members section.

**Rationale for placement** (resolves question #1):
- It is a **per-project** destructive action — belongs on the per-project page, not the global dashboard.
- Settings page is sibling-navigated via the existing sidebar entry (⚙️ Settings) — discoverable.
- Mirrors GitHub / Linear convention: destructive project-level operations live under Settings.
- Dashboard project cards (`home/+page.svelte:104-127`) are intentionally minimal and crowded would damage the existing visual rhythm.

#### State A — Idle (collapsed launcher)

```
┌─────────────────────────────────────────────────────────────┐
│  Linked Projects                                            │  ← 18px / 700 / accent
│                                                             │
│  Link this project to another one of your projects to       │  ← 14px / 400 / muted
│  merge their events and history. Useful when the same       │
│  repo got captured twice from different machines.           │
│                                                             │
│  [ + Link to existing project ]                             │  ← .btn-primary gradient pill
│                                                             │
└─────────────────────────────────────────────────────────────┘
```

- **Outer container:** `.glass` card style — `background: rgba(255,253,248,0.7)`, `backdrop-filter: blur(20px)`, 1px `var(--color-border)`, `border-radius: var(--radius-md)`, `padding: 2rem`.
- **Trigger button:** uses existing `.btn-primary` class from `app.css:151-165` (gradient maroon pill, white text, 600 weight, 14px, `padding: 12px 28px`, scales 1.03 on hover).
- **Button label (locked by D-07):** `Link to existing project` (with a leading `+ ` glyph to mirror the "+ New Project" button on `home/+page.svelte:64`).

#### State B — Expanded (picker open)

When the user clicks the trigger, the card expands inline (NOT a floating modal — matches `DangerZone.svelte` pattern):

- **Auto-match section** (resolves question #2): only rendered when `data.candidates.length > 0`. Uses subtle accent surface `background: rgba(86, 28, 36, 0.04)`, 1px accent border `rgba(86, 28, 36, 0.15)`, 12px radius, internal label "Suggested matches" at 12px / 700 / uppercase / `letter-spacing: 0.06em` / `--color-text-muted` (mirrors `AppShell.svelte:183-189` `switcher-group-label`). Each candidate row carries a small badge: text "Matched" with `background: rgba(86, 28, 36, 0.08); color: var(--color-pink-dark); font-size: 11px; font-weight: 600; padding: 2px 8px; border-radius: 9999px` — same shape as the existing `tool-badge` at `home/+page.svelte:336-343` but in accent muted, not vibrant. **This is the only NEW accent usage in Phase 2.**
- **Candidate rows:** radio-input style selection — one row selectable at a time. Layout: project name (13px / 600 / `--color-text`), inline meta (12px / 400 / `--color-text-muted`). Row container: `padding: 12px 16px`, `border-radius: 12px`, `border: 1px solid rgba(199, 183, 163, 0.25)` (mirrors `projects/[name]/+page.svelte:164-169` insight card). Hover: `border-color: var(--color-pink)` and `transform: translateY(-1px)` (mirrors `home/+page.svelte:295-299`).
- **Empty list under "Your other projects"** (resolves question #3): if the user has only this project (no other projects to link into), the picker shows:
  - Heading: `No other projects to link to`
  - Body: `Create another project from the home page first, then return here to link them.`
  - Action: a single ghost link `← Back to Home` (uses existing link styling). The primary trigger button on State A should be **disabled** with helper text `(You need at least 2 projects to link.)` in this case — do not open the expanded state at all.

After the user selects a target and clicks `Continue`, the inner card transforms (state machine — same card surface, replaced inner content). Mirrors `DangerZone.svelte:107-153` exactly:

```
│  "<target-name>" and permanently delete "<source-name>".    │
│                                                             │
│  [ Type "<source-name>" to confirm        ]                 │  ← text input
│                                                             │
│  [ Cancel ]            [ Link projects & delete source ]    │  ← .btn-danger; disabled until match
│                                                             │
└─────────────────────────────────────────────────────────────┘
```

- **Type-to-confirm input** (resolves question #7): `<source-project-name>` exact string match (case-sensitive, matches `DangerZone.svelte:117` `deleteInput === "DELETE"` pattern but parameterized by project name). Disable the confirm button until `confirmInput === sourceProjectName`.
- **Confirm button:** `.btn-danger` class — `background: var(--color-danger)`, white text, 600 weight, pill — copied from `DangerZone.svelte:159-176`.
- **Cancel button:** `.btn-secondary` class from `app.css:167-180`.

#### State D — Loading (request in flight)

(Resolves question #4.)

- The confirm button replaces its label with a spinner row: `<span class="spinner spinner-sm spinner-white"></span> Linking…` (mirrors `DangerZone.svelte:71-74`).
- Both buttons in the type-to-confirm panel become `disabled`. The text input becomes `readonly` (not `disabled` — preserves visual contrast).
- The expand/collapse trigger is non-interactive during the request.
- **Duration expectation:** 1-3s typical (server does owner-check ×2 → atomic SQL RPC → recompute target's `ProjectStatus`). No skeleton loaders needed at this duration.

#### State E — Success

(Resolves question #5.)

On 200 from the merge endpoint:
1. The picker card collapses back to State A — but the section heading + body copy are temporarily replaced with a green banner inside the same card (mirrors `home/+page.svelte:243-250` `.success-msg` and `DangerZone.svelte:23-30`):
   ```
   ✓ Linked successfully. Redirecting to <target-name>…
   ```
   Style: `background: var(--color-success-bg)`, `color: var(--color-success)`, `padding: 8-12px`, `border-radius: 8px`, `font-size: 13px`.
2. After 1200ms, the browser navigates to `/projects/<target-name-or-slug>` via SvelteKit's `goto()` (or `<a>` href in the response). The source project no longer exists, so navigating to the current page after merge would 404 — the redirect is mandatory.
3. No toast component exists in the codebase; do **not** introduce one. The inline success banner is sufficient.

#### State F — Error

(Resolves question #6.)

All errors render inline at the top of the picker card (mirrors `home/+page.svelte:87-89` `.error-msg` and `DangerZone.svelte:31-39`):
- Container: `background: rgba(139,0,0,0.06)`, `border: 1px solid rgba(139,0,0,0.2)`, `color: var(--color-danger)`, `padding: 8-12px`, `border-radius: 8px`, `font-size: 13px`, `role="alert"`.
- After an error, the picker stays in whichever state the user was in (B or C) — they can retry without re-selecting.

Error copy by class (full strings in Copywriting §):
- **Ownership mismatch (403):** "You're not the owner of one of these projects. Only the owner can link projects."
- **Backend 5xx:** "Something went wrong on our side. Wait a moment and try again — if it keeps failing, check the project page in a few minutes."
- **Network failure / timeout:** "Couldn't reach the server. Check your connection and try again."
- **Target project not found (404, race):** "That target project no longer exists. Refresh and pick another one."
- **Conflict (409, e.g., same project picked as source AND target):** "You can't link a project to itself. Pick a different target."

## Interaction Contracts

### State machine

```
            ┌───────────────────────────────────────────┐
            │                                           │
[A: idle]──click──►[B: picker open]──select+Continue──►[C: confirm gate]
   ▲                    │                                  │
   │                    └──click Cancel──┐                 │
   │                                     ▼                 │
   │                              [A: idle, cleared]       │
   │                                                       │
   │                                                       ▼
   │                                                 (type-match)
   │                                                       │
   │                                                       ▼
   │             ┌─────────────────┐                 click "Link…"
   │             │                 │                       │
[A: idle]◄─1200ms─[E: success]◄─200─[D: loading]◄─────────┘
                                       │
                                       └─4xx/5xx/timeout──►[F: error]
                                                                │
                                                                ▼
                                                       (stay in C; retry)
```

### Keyboard contract

- The trigger button (State A) receives focus normally in tab order.
- When the card expands to State B:
  - Focus moves to the **first focusable element inside the expanded panel** (the first candidate radio, if any, otherwise the Cancel button). Implementation: `bind:this` + `requestAnimationFrame` then `.focus()` — same pattern as native HTML.
  - Arrow Up/Down moves between candidate radios (browser-native behavior of grouped radios).
  - Tab order: candidates → Cancel → Continue.
  - `Escape` collapses to State A. Wire on the picker container's `onkeydown`. **The element is NOT a `<dialog>`** — there's no native focus trap. The expanded card stays in document flow; tabbing past it tabs into the next page section. This is acceptable for an inline expander (resolves question #8 — see Accessibility §).
- When the card transitions to State C:
  - Focus moves to the text input automatically.
  - Tab order: confirm-input → Cancel → "Link projects & delete source".
  - `Escape` collapses to State A (NOT to State B — explicit cancel is safer for destructive actions).
- During State D (loading), all controls are `disabled`; `Escape` is ignored.

### Click-outside behavior

Inline-expander cards in the existing codebase (`DangerZone.svelte`) do **not** auto-collapse on outside click. Phase 2 follows the same convention: outside click does nothing. Only `Cancel`, `Escape`, or completing/erroring the action changes state.

### Form submission

Use SvelteKit's `use:enhance` form action (the codebase convention — see `home/+page.svelte:69` `?/createProject` and `DangerZone.svelte:62,123`). Backend endpoint per RESEARCH.md: `POST /api/projects/:id/merge-into/:target_id`. Action handler in `+page.server.ts` posts to the backend with the user's session cookie + bearer token and returns `{ ok: true, project_id }` or `{ error, code }` shaped per the existing form-action conventions.

## Mobile / Responsive

(Resolves question #10.)

- The Settings page already uses `max-width: 3xl` (~768px) per `settings/+page.svelte:8` (`class="max-w-3xl"`). The new "Linked Projects" card inherits that constraint — naturally readable on tablet.
- **No separate mobile design.** At ≤480px viewport, the action buttons (Cancel + Continue / Cancel + Link projects & delete source) stack vertically rather than side-by-side — use `flex-wrap: wrap` on the button row (one-line CSS, planner detail).
- The candidate-row list scrolls within its container if the user has 20+ other projects. Cap at `max-height: 320px` with `overflow-y: auto` and a subtle inner shadow at the bottom edge — this prevents the picker from running off-screen.

## Claude's Discretion

These are open items the planner should resolve when sequencing tasks. They are **not** gating the contract.

1. **Component file layout.** The expandable picker is significant enough to extract to `frontend/src/lib/components/project-link/LinkPicker.svelte` (alongside an `account/` sibling), versus keeping it inline in `settings/+page.svelte`. Recommendation: extract — there are three internal states (B, C, D-or-F) and it's worth its own file. The success/error banners can stay inline.
2. **How candidates arrive at the frontend.** The page server load can either (a) eagerly fetch `GET /api/projects/me?with_match_candidates=true` on Settings page load, or (b) lazy-fetch when the user clicks the trigger button. Recommendation: eager (it's one extra DB query, the Settings page is already authenticated and project-scoped). Backend exposes this shape — planner names the route.
3. **Search/filter inside the picker.** Not in scope for Phase 2's MVP (D-07 says "full list below"). If the user has > ~10 projects the list gets long; the `max-height + scroll` mitigation in Mobile § covers it. Planner may add a search input later — out of scope here.
4. **`prefers-reduced-motion` honor.** See Accessibility § last row. Planner picks: match existing codebase (don't honor) or improve (honor).
5. **Optimistic UI vs request-then-redirect.** Recommended (and specified in State E above): request-then-redirect, no optimistic state. The action is destructive — optimism is wrong.
6. **Toast vs inline banner.** Locked: inline banner. No toast component exists; do not introduce one.
7. **Audit log surfacing.** RESEARCH.md says `logActivity` writes a `project_merged` row. Whether the merged-target's activity log displays it is out of scope for Phase 2 UI (the activity tab is rendered by an existing surface).

## Out of Scope

Considered and explicitly rejected for this phase:

- **Floating modal/dialog overlay.** No `<dialog>` primitive, no portal-rendered overlay, no scrim/backdrop. Inline-expanding card matches the project's existing destructive-action pattern (`DangerZone.svelte`). Introducing the first floating dialog component in Phase 2 would balloon scope.
- **Dashboard-list inline action.** "Link to existing project" does NOT appear as a per-row action on the home page project grid. Per-project Settings is the single placement.
- **Bulk merge.** Selecting and merging multiple source projects in one operation. One-to-one only.
- **Undo.** No undo path. Merge is destructive (events reassigned, source row deleted). The type-to-confirm gate is the safety mechanism.
- **Search / filter inside the picker.** See Discretion #3.
- **Toast notifications.** Not in the codebase; not introducing.
- **Icon library (lucide-svelte, heroicons, etc.).** Codebase uses unicode + emoji only.
- **Loading skeleton.** 1-3s wait is too short to justify a skeleton; the spinner-in-button pattern from `DangerZone.svelte` is enough.
- **Drag-and-drop merge.** Considered and rejected — slow, error-prone, no precedent in the app.
- **Animation polish beyond existing `transition-base`.** No motion-heavy interactions; the project is "minimal-functional" per the orchestrator brief.
- **A "Merge history" page.** Out of scope per the brief.
- **Mobile-specific flow.** See Mobile §.
- **`projects/[name]/settings` IA redesign.** Add a section; don't restructure.
