# Slice B: scoped-token minting + /cli-auth redirect_uri

Second slice of the self-sufficient extension. Reuses the existing PKCE web sign-in
(`/cli-auth` → `/auth/cli-session` → `/auth/cli-exchange`) but adds (1) the ability to
mint a **capture-scoped** key and (2) a strictly-validated `redirect_uri` so
`chrome.identity.launchWebAuthFlow` (which catches `https://<ext-id>.chromiumapp.org/`)
can complete the handshake instead of the CLI's localhost loopback.

Built + tested, then **held for review before push** (push auto-deploys the live auth path).

## Tasks

### Backend — capture-scope minting (feature-detection safe)
1. `createApiKey(db, userId, hash, label, expiresAt?, machineId?, scope?)` — append optional
   `scope`. Include `scope` in the INSERT **only when it is a non-default ('capture')** value,
   so every existing full-key insert stays byte-identical and cannot 500 before migration 031.
2. `cliSession` schema: add `scope: z.enum(['full','capture']).optional()`.
3. `mintCliSessionCode`: thread `scope` → `createApiKey`.
4. `/auth/cli-session`: when `scope === 'capture'`, take a dedicated branch —
   - label = `ext-browser` (fixed); does NOT match `cli-%`, so it never burns the device cap.
   - rotate-if-exists: one capture key per user. If an `ext-browser` key exists → `rotateApiKeyHash`
     (re-auth is idempotent, can't accumulate credentials); else `createApiKey(..., scope='capture')`.
   - skip the cli-device-cap 409 logic (capture keys aren't devices).
5. New query `findKeyByLabel(db, userId, label)` → `{id} | null` (capture-key lookup).

### Frontend — redirect_uri (the open-redirect guard)
6. `cli-params.ts`: add `redirect_uri` + `scope` to `CliParams`; extract `cli_redirect_uri` / `cli_scope`;
   preserve both in `buildRedirect`.
7. New `buildCallbackUrl(cli, code)` (+ `isAllowedExtensionRedirect`): returns the validated
   `redirect_uri`-based URL when present, else the existing `http://localhost:${port}/callback`.
   **Validator (allowlist-shaped, URL-parsed):** scheme === `https:` AND
   `hostname === <label>.chromiumapp.org` (hostname.endsWith('.chromiumapp.org'), parsed — defeats
   `…@evil.com`, `chromiumapp.org.evil.com`, path/userinfo tricks). Invalid → reject (no fallback to attacker URL).
8. `+page.server.ts` `load`: read `redirect_uri` + `scope` from `url.searchParams`; relax
   `hasCli` to `challenge && state && (port || redirect_uri)`.
9. `+page.server.ts` `continueAs` + `revokeAndContinue`: relax the `!cli.port` guard to
   `!(cli.port || cli.redirect_uri)`; forward `scope` in the `/auth/cli-session` body;
   build the callback via `buildCallbackUrl`.

## Tests
- Backend (`auth-cli-session` / new): scope=capture → key minted as capture + `ext-browser`;
  second call rotates (no new row); device-cap NOT consulted; default (no scope) → unchanged full path.
- Frontend (`cli-params.test.ts` + new): `isAllowedExtensionRedirect` accepts `https://x.chromiumapp.org/`,
  rejects http, `…@evil.com`, `x.chromiumapp.org.evil.com`, non-URL; `buildCallbackUrl` prefers a valid
  redirect_uri, falls back to port, and never emits an unvalidated redirect.

## Decisions / notes
- Capture key = single fixed-label (`ext-browser`) per user, rotate-on-reauth. Bounds credentials and
  matches "one signed-in browser identity." Global `API_KEY_MAX_PER_USER` is the backstop.
- `redirect_uri` is frontend-only — the backend just mints the code; the redirect happens client-side
  (`continueAs` returns `{redirectTo}`; the page navigates, Chrome catches the chromiumapp.org URL).
- PKCE already makes a leaked code unusable without the verifier; the allowlist is defense-in-depth.
