## Why (the gap that existed)

The billing happy path was untested. `billing-webhook-dispatch.test.ts` only pinned the `default:` branch and carried a **stale comment** claiming a fake `db` is a runtime no-op — but the dispatcher passes `db` straight through to the query layer, so state transitions ARE observable. `billing.test.ts` covered only negative HTTP paths. Nothing asserted that an event produces the correct status, that gating reads `status IN (active,past_due)`, or that a signed webhook reaches dispatch.

## Key findings (recorded as insights)

- **Access is gated on `status`, not `current_period_end`** (`getActiveSubscription` filters `status IN (active,past_due)`). So the known Creem renewal-webhook gap leaves a stale date but does NOT downgrade paying users.
- The real billing risk is a **knowledge gap**, not a code gap: it's unconfirmed whether Creem emits explicit `canceled`/`expired` on a true lapse (else a lapsed sub stays `active` = revenue leak). The new unknown-event test pins current inert behavior and will flip red the day a renewal case is added.
