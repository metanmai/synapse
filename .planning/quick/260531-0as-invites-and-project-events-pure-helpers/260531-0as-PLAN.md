## Out-of-scope endpoints (explicitly NOT in this round)

After reading the handlers, three of the remaining six 5a endpoints have minimal pure-extractable surface and are best served by path (a) (live Supabase) instead:

- **`project-status` (21 lines, all DB)** — handler is `select → maybeSingle → 404 or return`. No pure logic.
- **`auth-me` (5 lines)** — handler is `return c.json({ user_id, email, tier })`. The skipped tests assert the live-DB contract (user_id from `public.users` not `auth.users`), which only a real Supabase can verify.

These will be flagged in the BUGS.md 5a update as "path (a) preferred" so the user knows path (b) is exhausted on those.

## Targets

### 1. invites-pure.ts

Pure logic in `backend/src/api/invites.ts:8-14` and inline in the handlers:

- `generateInviteToken()` — 24 random bytes → 32-char base64url string. **Security-critical** because token entropy guards against guessing attacks; charset (no `+/=`) matters for URL safety. Currently a private function in invites.ts.
- `parseInviteRequestBody(raw)` — the try/catch JSON parse + email validation (non-empty trimmed string). Currently inline.
- `isInviteExpired(expires_at, now)` — `new Date(expires_at).getTime() < now`. Currently inline; date-math bug class.
- `isInviteAccepted(invite)` — `invite.accepted_at != null` check. Currently inline.
- `computeInviteExpiresAt(now, ttlMs)` — exposed for clarity.

Bug classes guarded:
- Token charset relaxed (e.g. removing the `+/=` replace), breaking URL safety
- Token length truncated by a refactor
- Token entropy collision (two calls return same token — guards against a non-crypto rand path slipping in)
- Body parser crashes on malformed JSON instead of returning 400
- Email validation accepts whitespace-only string
- Expiry off-by-one at exactly `expires_at == now` (boundary)

### 2. project-events-pure.ts

Pure logic in `backend/src/api/project-events.ts:11, 22`:

- `parseEventsLimit(rawLimit)` — `Math.min(parseInt(raw ?? "200", 10), 1000)`. Edge cases: missing, "abc" (NaN), negative, over-cap.
- `computeNextSince(events, fallbackSince)` — `events.length > 0 ? events[last].event_id : fallbackSince`. Currently inline; cursor logic.

Bug classes guarded:
- Limit cap removed accidentally (queries unbounded → cost explosion)
- `parseInt` returns NaN, which then defeats `Math.min` (returns NaN) → query returns no rows
- Negative limit accepted → DB query fails opaquely
- `computeNextSince` returns undefined on empty when fallback was a string (cursor regression on follow-up call)
